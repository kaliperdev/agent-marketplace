# Setup paths for the curated vendor MCPs

These are **documentation-verified setup drafts**, reviewed on 9 November 2026. They are not `connection.guide` entries yet: the repository's [guide standard](connection-guides.md) requires someone to follow every step with a fresh account before setting `checked`. Do not present these drafts as tested customer instructions. No vendor credentials belong in Slack chat.

On the catalog page, the eventual guide should appear next to **Sign in with…**, just as the [Google Docs guide](../agents/gdocs/catalog-2.0.3.json) appears next to its key form. Each guide needs prerequisites, what data the agent can access, one action per step, a vendor documentation link, a connection test, and fixes for errors observed during the hands-on run. Sign-in guides should finish with **Test connection** and **Save and turn on**.

## Ready for a one-click flow after a hands-on test

| Agent | Before connecting | Customer path | Access and test | First-party source |
|---|---|---|---|---|
| **ClickHouse Cloud** | A service admin enables Remote MCP for the service from **Connect → Connect with MCP**. | Select ClickHouse in Kaliper, choose **Sign in with ClickHouse Cloud**, approve OAuth, then test. | Only the signed-in user's accessible services and read-only tools. Ask for a database list and verify the intended service is present. | [ClickHouse Remote MCP](https://clickhouse.com/docs/products/cloud/features/ai-ml/mcp/remote-mcp) |
| **MotherDuck** | A MotherDuck account and access to the intended database. | Select MotherDuck, sign in through MotherDuck OAuth, then test. | The hosted MCP uses a read-only connection for its read tools. Ask for the accessible database list before enabling it for Slack. | [MotherDuck Remote MCP](https://motherduck.com/product/mcp-server/), [OAuth implementation](https://motherduck.com/blog/dev-diary-building-mcp/) |
| **Fellow** | A workspace admin enables **Workspace Settings → Fellow MCP → MCP connection**. | Select Fellow, sign in with the account that can see the meetings, then test. | It sees only meeting data already visible to that user. Search for a known meeting; if none appears, check the workspace setting and meeting permissions. | [Fellow MCP setup](https://help.fellow.ai/en/articles/12622641-fellow-s-mcp-server) |
| **Clarify** | A Clarify account in the organization to connect. | Select Clarify, sign in on its OAuth page, select the organization, and approve access. | It inherits the user's Clarify access. Query one known deal or meeting; check the chosen organization if results are empty. | [Clarify MCP](https://docs.clarify.ai/en/articles/13367278-clarify-mcp) |
| **Outreach** | An Outreach account with MCP/Amplify access and permission to read the intended records. | Select Outreach, sign in through Outreach SSO, and approve the requested OAuth scopes. | The server applies the signed-in user's RBAC. Search for a known opportunity; if access is denied, check product entitlement and RBAC. | [Outreach MCP authentication](https://developers.outreach.io/mcp-server/authentication), [tool catalog](https://developers.outreach.io/mcp-server/tool-catalog) |
| **Day AI** | A paid Day AI Agent tier, the workspace, and the agent identity the user intends to authorize. | Select Day AI, sign in, choose the workspace and agent, and approve OAuth. | Tools vary with the paid tier and agent. Test `search_objects` against a known person or company; the catalog exposes only read tools. | [Day AI MCP](https://day.ai/mcp), [Day AI tool list](https://github.com/day-ai/day-ai-sdk/blob/master/TOOLS.md) |

Public OAuth metadata advertises a `registration_endpoint` for [ClickHouse](https://mcp.clickhouse.cloud/.well-known/oauth-authorization-server), [Fellow](https://fellow.app/.well-known/oauth-authorization-server), [Clarify](https://auth1.clarify.ai/.well-known/oauth-authorization-server), and [Day AI](https://day.ai/.well-known/oauth-authorization-server). [MotherDuck](https://motherduck.com/blog/dev-diary-building-mcp/) and [Outreach](https://developers.outreach.io/mcp-server/authentication) document dynamic registration. This supports automatic client registration. The six flows still need a real end-to-end connection on a fresh account; public metadata does not prove that Kaliper's OAuth client, scopes, and router complete sign-in.

Step-specific **drafts** live under each agent's `guide/` folder: [ClickHouse](../agents/clickhouse/guide/README.md), [MotherDuck](../agents/motherduck/guide/README.md), [Fellow](../agents/fellow/guide/README.md), [Clarify](../agents/clarify/guide/README.md), [Outreach](../agents/outreach/guide/README.md), and [Day AI](../agents/day-ai/guide/README.md). The first five folders contain focused UI screenshots taken from official vendor pages. Day AI has no verified public setup-screen image. These are reference assets, not a published `connection.guide`: some show another MCP client's setup and all need replacement or confirmation during a real Kaliper connection.

## Requires a different sign-in implementation

The following four candidates are **deferred from the current PR**. Their earlier catalog drafts specified `signin.client: "automatic"`, but the first-party setup paths require a registered client, a supported-client allowlist, or an administrator provisioned configuration. Do not ask a customer to click an automatic sign-in button that cannot complete.

| Agent | What the vendor requires | Lowest-friction Kaliper path | First-party source |
|---|---|---|---|
| **Box** | Box's MCP server does not support Dynamic Client Registration. Its admin setup supplies a client ID and secret and registers the MCP client's redirect URI. | Register and publish a Kaliper Box app once, if Box's app and distribution rules allow it. Until then, use an explicit own-app flow with a guide and secure web form, or defer. | [Box MCP administration](https://support.box.com/hc/en-us/articles/43847256139923-Managing-Box-MCP-Servers) |
| **Zoom Meetings** | Zoom's MCP server requires manual OAuth app registration and product-specific scopes; it does not support DCR or CIMD. | Register a Kaliper Zoom app with the read scopes and required approval. Until then, an own-app guide would need the customer to create a General app and enter its client ID/secret. | [Zoom MCP connection](https://developers.zoom.us/docs/mcp/servers/connect-to-zoom-mcp-servers/) |
| **Salesforce SObject Reads** | A Salesforce org admin creates an External Client App, enables PKCE and JWT access tokens, adds `mcp_api` and `refresh_token` scopes, and registers Kaliper's callback URL. | Offer an admin-led setup wizard with exact callback URL and secure client ID field. A managed Kaliper app may reduce repeated work only if Salesforce's distribution model supports it. | [Salesforce client connection](https://developer.salesforce.com/docs/platform/hosted-mcp-servers/guide/client-connection-overview.html), [External Client App](https://developer.salesforce.com/docs/platform/hosted-mcp-servers/guide/create-external-client-app.html) |
| **MongoDB Atlas** | User-delegated App Connections works only for MongoDB's pre-registered AI clients. A custom client instead needs an admin-provisioned MCP configuration and service-account credentials. | Seek official Kaliper client registration. Otherwise implement a separate programmatic connection flow with a read-only configuration; the current automatic OAuth entry should be deferred. | [Atlas access models](https://www.mongodb.com/docs/mcp-server/remote-mcp/access-models/), [managed MCP setup](https://www.mongodb.com/docs/mcp-server/get-started/) |

## Publishing gate

Before adding `connection.guide` to a catalog, follow its vendor flow on a fresh account, record the date in `checked`, verify the vendor's current labels and permission prompts, capture any real error messages for `trouble`, test a harmless read tool, and confirm the result in the Kaliper catalog page at phone width and in both themes. A guide that needs a customer's own app or key must be present before that catalog version is published.
